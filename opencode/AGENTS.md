When a project's rules change, update its AGENTS.md — extend existing sections where possible, prune what becomes stale, and don't append narration of routine code changes (commit messages cover that).

Never `git commit` or `git push` on your own initiative — in any repo, including when a project's workflow (CI-on-merge, PR flow) makes it convenient. Prepare the changes, leave the branch/working tree ready, and tell the user it's ready; only commit or push when they explicitly ask in that request. Project conventions about commit style apply only once the user has asked for the commit.

## DRY — "Every piece of knowledge must have a single, unambiguous, authoritative representation within a system" (Hunt & Thomas, The Pragmatic Programmer)

Apply DRY broadly — not just code (dedupe via functions/abstractions) but database schemas, test plans, build systems, and documentation too. Prefer abstractions that are unlikely to change, or normalize data so redundancy never exists. Done right, changing one element never requires touching logically unrelated elements, and related elements change predictably and stay in sync. When you find yourself copy-pasting knowledge across files, extract it to its single authoritative source instead.

Try to refrain from using insider lingo when talking about finances.

## Browser automation — agent-browser

Config lives in `~/.agent-browser/config.json` (symlink to `~/dotfiles/agent-browser/config.json`): hardware-GPU launch args (`--use-angle=vulkan,--enable-features=Vulkan` — WebGL renders on the RTX 4070 Ti instead of SwiftShader-on-CPU, which pegs every core at ~1300%) and a 5-minute idle timeout that auto-closes the headless browser. Still run `agent-browser close --all` when done with a browser task. If a `chrome --type=gpu-process` under `~/.agent-browser/browsers/` ever spins up CPU again, it means the config was bypassed/overridden — check the config first, don't just pkill. Kill scoped with `pkill -f '.agent-browser/browsers/chrome'`; never blanket `pkill chrome` (Steam and other apps embed Chrome). Do not attach to the user's running Helium browser (`--connect`/`--auto-connect`) — that hijacks their tabs and personal session.

The `google-ads` MCP server is FGRibreau/mcp-google-ads (Rust; rebuild at `~/git_clones/mcp-google-ads` with `cargo build --release` after pulling). It targets Google Ads account `4666587905` (GiveMeAJob) with direct OAuth access — no `GOOGLE_ADS_LOGIN_CUSTOMER_ID` needed. Since the 2026-09-09 developer-token sunset, the API does not validate the `developer-token` header: `GOOGLE_ADS_DEVELOPER_TOKEN` in `~/.zsh_api_keys` is an inert placeholder, and API access level is tied to the `dan-marketing-mcp-01` Google Cloud project (Test level; Explorer application pending). Auth uses the authorized-user ADC at `~/.config/google-ads/user-adc.json`, split into `~/.mcp-google-ads/credentials.json` (`installed` OAuth-client format) and `~/.mcp-google-ads/token.json` (refresh token) — the server requires both. API versions ≤v22 are blocked; the server defaults to v25 (`GOOGLE_ADS_API_BASE_URL` overrides). The manager account `Dan API MCC` (917-819-2119) exists only as a container; its API Center form handles just the App Conversion Tracking API. `google-ads-official` is the official `uvx google-ads-mcp` and uses the ADC directly. Querying production accounts additionally requires the account to allow it.
